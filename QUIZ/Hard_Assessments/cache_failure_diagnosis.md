# 快取故障診斷：區分穿透、擊穿與雪崩

- **Assessment ID**: `assessment.backend.cache.failure-diagnosis.v1`
- **主要 Concept ID**: `concept.backend.cache.failure-modes`
- **對應文章**: [快取穿透、快取擊穿和快取雪崩](../../02_Backend_Development/Caching/cache_penetration_breakdown_avalanche.md)
- **題型**: `故障診斷`, `容量保護`, `權衡取捨`
- **難度**: 8
- **重要程度**: 5
- **建議作答時間**: 15 分鐘
- **標籤**: `Redis`, `Cache Penetration`, `Cache Breakdown`, `Cache Avalanche`, `High Availability`
- **Learning Objective IDs**: `LO-1`, `LO-2`, `LO-3`

## 測驗目標

- **LO-1**：能根據症狀區分快取穿透、快取擊穿與快取雪崩，並定位主要故障層級。
- **LO-2**：能設計包含鎖、TTL、限流、熔斷與降級的分層防護，說明失效時的退化行為。
- **LO-3**：能以命中率、回源流量、Redis 與資料庫資源等指標驗證診斷，並評估資料新鮮度與可用性取捨。

## 問題詳述

某商品服務在同一個時段出現三組現象：

- 流量中有大量從未出現過、且格式合法的商品 ID；快取與資料庫都查不到這些 ID。
- 熱門商品 `product:42` 過期後，數千個請求同時查詢資料庫。
- Redis 叢集重新選主時，大量原本存在的快取同時失效，資料庫連線池很快耗盡。

請設計一個能保護資料庫的處理方案，並說明哪些方案會引入過期資料或誤判。

## 核心測驗

### 作答要求

1. 將三組現象分別分類為快取穿透、快取擊穿或快取雪崩，並說明分類依據。
2. 為每組現象選擇至少兩種防護機制，說明它們應放在哪一層，以及失效時的退化行為。
3. 設計熱門 Key 重建流程，回答如何避免多個應用節點同時回源，以及鎖逾時時如何避免永久阻塞。
4. 說明空值快取、布隆過濾器、邏輯過期、隨機 TTL、熔斷與限流的副作用。
5. 列出你會監控的至少五個指標，讓值班人員能區分三種故障。

### 期待證據

- 能用「不存在資料、單一熱點失效、大量資料或快取層整體失效」區分三種問題。
- 能說明互斥鎖需要 TTL、持有者識別與失敗重試策略，不能只寫 `SETNX`。
- 能指出邏輯過期可以降低延遲，但會暫時回傳舊資料。
- 能將快取命中率、回源 QPS、資料庫連線池、Redis 錯誤率、熱點 Key、空值比例與延遲連在一起分析。

## 評分規準

| 分數 | 期待表現 |
| :---: | :--- |
| 0 | 無法區分三種快取故障 |
| 1 | 能背出名稱與單一解法，但沒有故障流程 |
| 2 | 分類大致正確，但忽略鎖安全、資料新鮮度或退化行為 |
| 3 | 能完成分類、分層防護、指標與主要取捨分析 |
| 4 | 能設計在併發、Redis 故障、熱點重建與資料更新同時發生時仍可控的方案 |

### 通過標準

預設 3/4 通過。

## 參考答案與詳解

<details>
<summary>顯示參考答案</summary>

- 第一組是快取穿透：資料在快取與資料庫都不存在。可使用短 TTL 空值快取與布隆過濾器，但要處理大量不同惡意 Key、布隆過濾器更新與誤判。
- 第二組是快取擊穿：單一熱點 Key 失效造成併發回源。可用帶 TTL 的分散式互斥鎖、single-flight 或邏輯過期；邏輯過期用舊資料換取可用性，鎖方案則需處理等待、逾時與持有者失效。
- 第三組是快取雪崩：大量 Key 同時失效或快取叢集故障。可用 TTL 隨機化、多層快取、限流、熔斷、降級與資料庫連線池保護；高可用 Redis 只能降低故障機率，不能消除回源尖峰。
- 監控至少應包含命中率、回源 QPS、按 Key 的請求分布、Redis 錯誤／延遲、資料庫連線池使用率、空值快取比例、鎖等待與應用錯誤率。

</details>

## 常見失分點

- 把單一熱點失效稱為雪崩，或把不存在資料稱為擊穿。
- 只建議「Redis 做叢集」，沒有處理快取同時失效後的資料庫壓力。
- 使用永不過期或邏輯過期時，沒有說明資料新鮮度與更新失敗。
- 建議分散式鎖卻沒有 TTL、重試上限與故障處理。
