# TCP 連接診斷：從狀態與指標定位問題

- **Assessment ID**: `assessment.network.tcp.connection-diagnosis.v1`
- **主要 Concept ID**: `concept.network.tcp.connection-management`
- **對應文章**: [TCP 三次握手與四次揮手](../../01_Computer_Science_Fundamentals/Networking/tcp_handshake_and_termination.md)
- **題型**: `追蹤`, `故障診斷`, `權衡取捨`
- **難度**: 8
- **重要程度**: 5
- **建議作答時間**: 15 分鐘
- **標籤**: `TCP`, `TIME_WAIT`, `CLOSE_WAIT`, `SYN Flood`, `可觀測性`
- **Learning Objective IDs**: `LO-1`, `LO-2`, `LO-3`

## 測驗目標

- **LO-1**：能依 TCP 狀態與連線生命週期，區分 `SYN-RECV`、`TIME_WAIT`、`CLOSE_WAIT` 所代表的階段與可能故障層級。
- **LO-2**：能根據連線狀態、速率、重傳與資源指標提出可驗證的故障假設。
- **LO-3**：能在連線池、Keep-Alive、防護機制與核心佇列調整之間做出有取捨的修復方案。

## 問題詳述

某 API 服務部署後出現連線逾時。監控資料顯示：

- 部分節點的 `SYN-RECV` 從 2,000 升到 50,000，應用程式的 `accept` 速率沒有同步增加。
- 另一批節點的 `TIME_WAIT` 從 5,000 升到 180,000，這些節點的短連線比例也明顯上升。
- 少數節點的 `CLOSE_WAIT` 持續增加，且數量不會在流量下降後恢復。

請不要直接假設「把所有 TCP 佇列調大」就是解法，完成下列分析。

## 核心測驗

### 作答要求

1. 分別說明 `SYN-RECV`、`TIME_WAIT`、`CLOSE_WAIT` 代表連接生命週期中的哪個階段，以及它們主要指向網路層、核心資源還是應用程式層問題。
2. 為每個現象提出至少一個最可能原因與一個需要驗證的替代假設。
3. 設計一個由應用程式、作業系統與負載均衡器組成的排查順序，列出應觀察的指標或命令。
4. 提出修復優先順序，並說明連接池、Keep-Alive、SYN Cookie、佇列調整與應用程式關閉連接各自的取捨。

### 期待證據

- 能區分「握手尚未完成」、「主動關閉後等待」與「被動關閉後應用程式尚未關閉」三種狀態。
- 不把 `TIME_WAIT` 直接判定為 bug，也不把 `CLOSE_WAIT` 歸因於核心參數。
- 能先以連接建立／關閉速率、逾時、重傳、accept backlog 與應用程式資源使用量驗證假設，再提出調校。
- 能說明短連線、連接重用、SYN Flood 防護與調大佇列之間的代價。

## 評分規準

| 分數 | 期待表現 |
| :---: | :--- |
| 0 | 無法正確解釋主要 TCP 狀態，或把三種現象視為同一問題 |
| 1 | 能說出部分狀態名稱，但無法將狀態連到故障層級 |
| 2 | 能辨認大部分原因，但排查順序或修復方案缺少驗證與取捨 |
| 3 | 能正確區分三種現象，提出分層排查流程與合理修復順序 |
| 4 | 能整合狀態機、監控證據、應用程式行為與核心調校邊界，並指出誤判風險 |

### 通過標準

預設 3/4 通過。

## 參考答案與詳解

<details>
<summary>顯示參考答案</summary>

- `SYN-RECV` 表示伺服器已回覆 `SYN+ACK`，仍在等待客戶端完成握手。大量增加可能與 SYN Flood、上游連線建立失敗、網路丟包或半連接佇列不足有關；應檢查 SYN 重傳、來源分布、負載均衡器與 `tcp_max_syn_backlog`，不能只看總數。
- `TIME_WAIT` 通常出現在主動關閉連接的一方。大量增加通常表示短連線或連線重建增加，應優先檢查 Keep-Alive、連接池、部署造成的連線重置與下游服務延遲。它本身是 TCP 正常保護機制，不等於連線洩漏。
- `CLOSE_WAIT` 表示本端已收到對方的 `FIN`，但應用程式尚未呼叫關閉。持續增加且不回落，優先懷疑應用程式未釋放 socket、錯誤路徑漏掉 close，或請求處理卡住。
- 排查應先建立時間線：連接建立／關閉速率、SYN／ACK 重傳、狀態分布、accept backlog、應用程式 goroutine／thread 與檔案描述符，再檢查負載均衡器和網路設備。只有在證據支持時，才調整佇列或啟用防護；長期修復通常是連接重用、正確關閉資源與降低不必要的重連。

</details>

## 常見失分點

- 看到 `TIME_WAIT` 就直接建議縮短等待時間。
- 把 `CLOSE_WAIT` 說成「對方沒有關閉連接」。
- 只列出 `sysctl` 參數，沒有說明如何驗證問題是否真的來自佇列。
- 沒有區分 SYN Flood 與正常的上游流量尖峰。
