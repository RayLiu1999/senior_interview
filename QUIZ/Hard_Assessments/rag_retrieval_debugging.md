# RAG 故障診斷：區分檢索失敗與生成失敗

- **Assessment ID**: `assessment.ai.rag.retrieval-debugging.v1`
- **主要 Concept ID**: `concept.ai.rag.retrieval-generation-pipeline`
- **對應文章**: [RAG 架構設計與實現](../../02_Backend_Development/AI_and_Machine_Learning/LLM_Integration/rag_architecture.md)
- **題型**: `故障診斷`, `檢索評估`, `成本與延遲權衡`
- **難度**: 8
- **重要程度**: 5
- **建議作答時間**: 20 分鐘
- **標籤**: `RAG`, `Retrieval`, `Reranking`, `Evaluation`, `Observability`
- **Learning Objective IDs**: `LO-1`, `LO-2`, `LO-3`

## 測驗目標

- **LO-1**：能根據候選文件、排序結果與生成輸出，區分文件處理、檢索、重排序與生成階段的故障。
- **LO-2**：能設計混合搜尋、版本過濾、引用約束與低相關度拒答等可驗證的改進方案。
- **LO-3**：能在 P95 延遲與 Token 成本限制下，使用檢索、答案品質、可追溯性與延遲指標評估取捨。

## 問題詳述

企業知識庫問答服務最近出現兩類回報：

- 使用者問「如何撤銷 API 金鑰」時，向量搜尋 Top-5 沒有找到正確文件，但關鍵字搜尋可以找到標題含有「API key revoke」的文件。
- 另一個問題中，Top-5 已包含正確且最新的政策文件，但模型回答時引用了舊版本內容。服務目前 P95 延遲為 1.8 秒，平均每次請求使用的上下文也偏大。

請判斷問題發生在哪個階段，並在延遲與成本受限的情況下提出改進方案。

## 核心測驗

### 作答要求

1. 將兩類問題分別定位到文件處理、Embedding、檢索、重排序、Prompt 或生成／後處理階段，並說明需要哪些觀測證據。
2. 為第一類問題設計改進方案，至少比較向量搜尋、BM25 混合搜尋、Query Rewriting 與 Reranking 的適用條件與成本。
3. 為第二類問題設計來源與版本控制方案，避免模型使用過期文件或無法指出引用來源。
4. 在 P95 延遲不能超過 2 秒的前提下，提出 Top-K、重排序數量、上下文長度與模型選型的取捨。
5. 設計至少四個離線或線上評估指標，區分「找不到正確文件」和「找到了但回答錯誤」。

### 期待證據

- 能把 RAG 拆成索引階段與查詢階段，並指出每個階段的可觀測輸出。
- 能區分 Retrieval Recall／MRR 與最終答案正確率，不能只用使用者點讚率判斷檢索品質。
- 能說明混合搜尋與重排序會增加延遲與成本，並提出分層或條件式啟用策略。
- 能處理文件版本、metadata filter、引用來源、低相關度結果與「沒有足夠資料時拒答」的情況。

## 評分規準

| 分數 | 期待表現 |
| :---: | :--- |
| 0 | 無法區分檢索失敗與生成失敗 |
| 1 | 能列出 Embedding、向量資料庫與 LLM，但沒有診斷證據 |
| 2 | 能提出混合搜尋或重排序，但忽略延遲、版本與評估方法 |
| 3 | 能分層定位兩類問題，提出可量化的改進方案與主要取捨 |
| 4 | 能建立完整的檢索／生成評估閉環，在延遲、成本、正確率與可追溯性間做出可驗證的設計 |

### 通過標準

預設 3/4 通過。

## 參考答案與詳解

<details>
<summary>顯示參考答案</summary>

- 第一類主要是檢索問題：向量結果沒有召回正確文件，但關鍵字能找到，表示語義嵌入、查詢表達或向量索引對術語匹配不足。可使用向量 + BM25 混合搜尋，先擴大候選集，再只對候選結果做小規模重排序；Query Rewriting 適合查詢含糊或上下文不足的情況，但會增加一次模型呼叫。
- 第二類至少包含來源排序或生成約束問題。應在 metadata 中保存文件版本與生效時間，先過濾過期文件，再在 Prompt 中要求只根據指定來源回答，並回傳 chunk ID／文件版本。仍需保留「模型可能忽略上下文」的生成評估。
- 延遲預算可分配為 Embedding、初步檢索、重排序與生成四段；例如只對 Top-20 做重排序、對高風險查詢啟用更強模型，並快取穩定查詢的 Embedding 或檢索結果。具體數值需用實驗驗證。
- 評估應至少分開記錄 Recall@K 或 MRR、引用正確率、答案正確率／忠實度、拒答準確率與 P95 延遲／Token 成本。只有檢索結果正確但答案錯誤時，才應把優化焦點移到 Prompt、模型或後處理。

## 常見失分點

- 把所有錯誤都歸因於 Prompt Engineering。
- 只增加 Top-K，卻沒有考慮上下文窗口、噪音與延遲。
- 宣稱 RAG 可以消除幻覺，沒有設計低相關度拒答與引用驗證。
- 只看最終答案，不記錄候選文件、版本、分數與重排序結果。
