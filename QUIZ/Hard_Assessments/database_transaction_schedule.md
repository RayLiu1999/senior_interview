- **標籤**: `Transaction`, `ACID`, `Isolation`, `MVCC`, `Concurrency`

## 測驗目標

- **LO-1**：能依交易時間線判斷髒讀、不可重複讀、幻讀與 lost update 等併發現象。
- **LO-2**：能辨識隔離級別、資料庫鎖定與應用程式條件檢查之間的責任邊界。
- **LO-3**：能比較悲觀鎖、樂觀鎖、原子更新與序列化交易在正確性、吞吐量、等待與重試成本上的取捨。

## 問題詳述

你正在診斷一個訂單服務。服務使用資料庫儲存帳戶餘額與訂單資料，最近發現偶發的重複扣款與報表筆數不一致。請用交易執行順序分析問題，而不是只背出 ACID 定義。

## 核心測驗

### 作答要求

請依序回答情境 A、B、C，逐步說明交易執行順序、可觀察證據與判斷理由，並比較不同隔離、鎖定或資料模型方案在正確性、吞吐量、等待、死鎖與重試成本上的取捨。

### 情境 A：同一筆資料的讀寫

初始餘額為 100。兩個交易執行以下操作：

| 順序 | 交易 T1 | 交易 T2 |
| :---: | :--- | :--- |
| 1 | 讀取餘額，得到 100 |  |
| 2 |  | 將餘額改為 80，但尚未提交 |
| 3 | 再次讀取餘額 |  |
| 4 |  | 回滾 |

請說明在不同隔離級別下，T1 第 3 步可能看到什麼，以及哪一種併發問題會發生。

### 情境 B：庫存扣減

庫存只剩 1 件。T1 與 T2 同時讀到庫存為 1，接著各自計算扣減後的值並提交。兩筆訂單都回報成功，但最終庫存只扣除一次。

請回答：

1. 這是哪一種併發錯誤？為什麼單純把資料庫改成 `Repeatable Read` 不一定能解決？
2. 請提出兩種修復方式，並比較悲觀鎖、樂觀鎖、原子條件更新與序列化交易的取捨。

### 情境 C：範圍報表

T1 在同一個報表交易中兩次查詢「金額大於 10,000 的訂單」；兩次查詢之間，T2 新增一筆符合條件的訂單並提交。請說明這個現象與不可重複讀的差異，以及你會如何依報表需求選擇隔離級別。

### 期待證據

- 能以交易時間線說明髒讀、不可重複讀、幻讀與 lost update 的差異。
- 能指出隔離級別保護的是資料庫的併發可見性，不會自動替應用程式完成業務條件檢查。
- 能提出至少一種資料庫層方案與一種應用／資料模型方案，並說明吞吐量、等待、死鎖或重試成本。
- 能區分 SQL 標準語意與特定引擎（例如 InnoDB MVCC 與 next-key lock）的實際行為。

預設 3/4 通過。

## 參考答案與詳解

<details>
<summary>顯示參考答案</summary>

- 情境 A 中，只有允許讀取未提交資料的隔離級別可能讓 T1 讀到 80；T2 回滾後，T1 讀到的值就不是有效提交狀態，因此是髒讀。較高隔離級別會避免讀到未提交版本，但具體快照行為仍取決於資料庫引擎。
- 情境 B 是 lost update 或 check-then-act 競爭。兩個交易都根據相同舊值計算，最後一次寫入覆蓋前一次結果。可用 `UPDATE ... WHERE stock > 0` 類型的原子條件更新、版本號樂觀鎖、行鎖或序列化交易；選擇取決於衝突率、等待時間、重試成本與是否需要跨多筆資料維持不變量。
- 情境 C 是範圍查詢的幻讀：結果集中出現原本不存在的新行。報表若要求交易內固定快照，可使用支援該語意的快照／可重複讀；若只需近似即時結果，較低隔離級別可能換取更高併發。不能只用資料庫名稱推斷所有行為，應以目標引擎文件與實驗驗證。

</details>

## 常見失分點

- 把 lost update 當成髒讀。
- 說 `Serializable` 會讓所有操作完全沒有併發，而沒有討論實作與等待。
- 忽略「讀取、條件檢查、寫入」之間的競爭窗口。
- 只談資料庫隔離，沒有說明冪等鍵、版本號或重試策略。
