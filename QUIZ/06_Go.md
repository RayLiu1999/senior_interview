### Q1: Goroutine 和 Thread 有什麼區別？
<!-- Concept ID: concept.go.concurrency.goroutine-scheduling; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐ (4) | **重要性**: 🔴 必考

請解釋 Goroutine 的工作原理，以及它與作業系統執行緒的差異。

<details>
<summary>💡 答案提示</summary>

| 特性 | Goroutine | OS Thread |
|------|-----------|-----------|
| **記憶體開銷** | ~2KB（可動態增長） | ~1-8MB（固定堆疊） |
| **創建成本** | 極低 | 高（系統調用） |
| **調度方式** | Go Runtime（用戶態） | OS Kernel（核心態） |
| **上下文切換** | 快速 | 較慢 |

**GMP 調度模型**：
- **G (Goroutine)**：執行的任務
- **M (Machine)**：作業系統執行緒
- **P (Processor)**：調度器（邏輯處理器）

**關鍵點**：
- Goroutine 是協作式調度
- Runtime 在特定時機（函數調用、Channel 操作等）插入調度點
- 可以輕鬆創建數萬個 Goroutine

</details>

### Q2: Buffered Channel 和 Unbuffered Channel 有什麼區別？
<!-- Concept ID: concept.go.concurrency.channel-buffering; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐ (5) | **重要性**: 🔴 必考

這是 Go 並行編程的核心概念，請解釋兩者的行為差異和適用場景。

<details>
<summary>💡 答案提示</summary>

| 特性 | Unbuffered | Buffered |
|------|------------|----------|
| **創建方式** | `make(chan T)` | `make(chan T, n)` |
| **發送阻塞** | 等待接收方 | 緩衝區滿時 |
| **接收阻塞** | 等待發送方 | 緩衝區空時 |
| **同步語義** | 同步通訊 | 異步通訊 |

**Unbuffered 用途**：
- 需要嚴格同步的場景
- 確保發送和接收同時發生
- 常用於信號傳遞

**Buffered 用途**：
- 生產者消費者模式
- 削峰填谷
- 避免 Goroutine 阻塞

**注意**：關閉已關閉的 Channel 會 panic！

</details>

### Q3: Select 語句的工作原理和應用場景是什麼？
<!-- Concept ID: concept.go.concurrency.select-multiplexing; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐ (6) | **重要性**: 🔴 必考

請解釋 select 如何實現多路複用，以及常見的使用模式。

<details>
<summary>💡 答案提示</summary>

**Select 特性**：
- 同時監聽多個 Channel
- 隨機選擇一個可用的 case 執行
- 沒有可用 case 時阻塞（除非有 default）

**常見模式**：

**1. 超時控制**：
```go
select {
case result := <-ch:
    // 處理結果
case <-time.After(time.Second):
    // 超時處理
}
```

**2. 非阻塞操作**：
```go
select {
case ch <- data:
    // 發送成功
default:
    // Channel 滿，跳過
}
```

**3. 優雅退出**：
```go
select {
case <-done:
    return
case data := <-workCh:
    process(data)
}
```

</details>

### Q4: Mutex 和 RWMutex 的區別是什麼？
<!-- Concept ID: concept.go.concurrency.read-write-locks; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐ (5) | **重要性**: 🟡 重要

請比較這兩種鎖的使用場景和效能特性。

<details>
<summary>💡 答案提示</summary>

| 特性 | Mutex | RWMutex |
|------|-------|---------|
| **鎖類型** | 互斥鎖 | 讀寫鎖 |
| **讀操作** | 互斥 | 可並行 |
| **寫操作** | 互斥 | 互斥 |
| **適用場景** | 讀寫均衡 | 讀多寫少 |

**RWMutex 方法**：
- `RLock()` / `RUnlock()`：讀鎖
- `Lock()` / `Unlock()`：寫鎖

**選擇指南**：
- 讀寫比例 > 10:1 → RWMutex
- 讀寫均衡 → Mutex
- 臨界區很小 → 可能 Mutex 更快

**注意事項**：
- 不要複製 Mutex
- 必須 Unlock 同一個鎖
- 避免死鎖（鎖順序一致）

</details>

<a id="q5"></a>
### Q5: WaitGroup 如何正確使用？
<!-- Concept ID: concept.go.concurrency.waitgroup-synchronization; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐ (4) | **重要性**: 🟡 重要

請說明 WaitGroup 的用途和常見錯誤。

<details>
<summary>💡 答案提示</summary>

**WaitGroup 用途**：等待一組 Goroutine 完成

**三個方法**：
- `Add(n)`：增加計數器
- `Done()`：減少計數器（等同於 `Add(-1)`）
- `Wait()`：阻塞直到計數器歸零

**正確用法**：
```go
var wg sync.WaitGroup

for i := 0; i < 5; i++ {
    wg.Add(1)  // 在啟動 Goroutine 前調用
    go func() {
        defer wg.Done()
        // 工作...
    }()
}

wg.Wait()  // 等待所有完成
```

**常見錯誤**：
1. 在 Goroutine 內部調用 `Add()`
2. 忘記調用 `Done()`
3. `Add()` 和實際 Goroutine 數量不匹配
4. 計數器變成負數（panic）

</details>

<a id="q6"></a>
### Q6: Go 的垃圾回收機制是如何工作的？
<!-- Concept ID: concept.go.internals.concurrent-gc; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐⭐⭐ (8) | **重要性**: 🟡 重要

請解釋三色標記法和寫屏障的原理。

<details>
<summary>💡 答案提示</summary>

**三色標記法**：

| 顏色 | 含義 |
|------|------|
| **白色** | 未訪問，可能是垃圾 |
| **灰色** | 已訪問，子物件待掃描 |
| **黑色** | 已訪問，子物件已掃描 |

**流程**：
1. 初始：所有物件為白色
2. 標記：從根開始，灰 → 掃描子物件 → 黑
3. 清除：剩餘白色物件為垃圾

**寫屏障**：
- 解決並發標記時的物件丟失問題
- 當黑色物件引用白色物件時，將白色變灰

**GC 觸發條件**：
- 堆記憶體增長到閾值
- 手動 `runtime.GC()`
- 超過 2 分鐘未 GC

**優化建議**：
- 減少小物件分配
- 使用 sync.Pool
- 預分配 slice 容量

</details>

<a id="q7"></a>
### Q7: Defer 的執行時機和順序是什麼？
<!-- Concept ID: concept.go.internals.defer-return-values; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐ (6) | **重要性**: 🟡 重要

請解釋 defer 的工作原理、執行順序，以及與 return 的關係。

<details>
<summary>💡 答案提示</summary>

**基本規則**：
1. defer 在函數返回**之前**執行
2. 多個 defer 按 **LIFO（後進先出）** 順序執行
3. defer 的參數在**聲明時**求值

**與 return 的關係**：
```go
func example() (result int) {
    defer func() { result++ }()
    return 0  // result 最終為 1
}
```

**執行順序**：
1. 計算返回值
2. 執行 defer
3. 返回

**常見用途**：
- 資源釋放（文件、鎖）
- panic 恢復
- 日誌記錄

**陷阱**：
```go
for i := 0; i < 3; i++ {
    defer fmt.Println(i)  // 輸出：2, 1, 0
}
```

</details>

### Q8: Slice 和 Array 的區別是什麼？
<!-- Concept ID: concept.go.internals.slice-array-representation; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐ (4) | **重要性**: 🔴 必考

請解釋 Slice 的底層結構和擴容機制。

<details>
<summary>💡 答案提示</summary>

| 特性 | Array | Slice |
|------|-------|-------|
| **長度** | 固定 | 動態 |
| **傳遞方式** | 值傳遞（拷貝） | 引用傳遞 |
| **聲明** | `[5]int` | `[]int` |

**Slice 底層結構**：
```go
type slice struct {
    ptr *T     // 指向底層陣列
    len int    // 長度
    cap int    // 容量
}
```

**擴容規則（Go 1.18+）**：
- cap < 256：翻倍
- cap >= 256：增長 `(cap + 3*256) / 4`

**常見陷阱**：
```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]  // b 與 a 共用底層陣列
b[0] = 100   // a[1] 也變成 100！
```

**最佳實踐**：
- 使用 `make([]T, len, cap)` 預分配
- 需要獨立副本時使用 `copy()`

</details>

### Q9: Context 套件如何使用？
<!-- Concept ID: concept.go.standard-library.context-cancellation; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐⭐ (7) | **重要性**: 🔴 必考

請解釋 Context 的設計理念、常用函數和使用規範。

<details>
<summary>💡 答案提示</summary>

**Context 用途**：
- 請求取消傳遞
- 超時控制
- 請求範圍內的值傳遞

**常用函數**：

| 函數 | 用途 |
|------|------|
| `context.Background()` | 根 Context |
| `context.WithCancel()` | 可取消的 Context |
| `context.WithTimeout()` | 帶超時的 Context |
| `context.WithDeadline()` | 帶截止時間的 Context |
| `context.WithValue()` | 傳遞請求範圍的值 |

**使用規範**：
1. Context 作為函數**第一個參數**
2. 不要將 Context 存在結構體中
3. 不要傳遞 nil Context
4. WithValue 只用於請求範圍的數據

**超時控制範例**：
```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()

select {
case <-ctx.Done():
    return ctx.Err()  // 超時或取消
case result := <-ch:
    return result
}
```

</details>

### Q11: 如何開發 Gin 中間件？
<!-- Concept ID: concept.go.gin.middleware-chain; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐ (6) | **重要性**: 🔴 必考

請解釋中間件的執行流程和常見的中間件類型。

<details>
<summary>💡 答案提示</summary>

**中間件本質**：`gin.HandlerFunc`

**執行流程**：
```
Request → Middleware1 → Middleware2 → Handler → Middleware2 → Middleware1 → Response
```

**c.Next() 的作用**：
- 執行後續的處理函數
- 形成「洋蔥模型」

**中間件範例**：
```go
func Logger() gin.HandlerFunc {
    return func(c *gin.Context) {
        start := time.Now()
        
        c.Next()  // 執行後續處理
        
        latency := time.Since(start)
        log.Printf("耗時: %v", latency)
    }
}
```

**常見中間件**：
- 日誌記錄
- 認證授權
- 錯誤恢復（Recovery）
- 限流
- CORS

**c.Abort() vs c.Next()**：
- `Abort()`：中止後續處理
- `Next()`：繼續執行

</details>

### Q13: 如何避免 Goroutine 洩漏？
<!-- Concept ID: concept.go.concurrency.goroutine-scheduling; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐⭐ (7) | **重要性**: 🔴 必考

請說明 Goroutine 洩漏的常見原因和預防措施。

<details>
<summary>💡 答案提示</summary>

**常見洩漏原因**：

| 原因 | 說明 |
|------|------|
| Channel 阻塞 | 無人接收/發送 |
| 無限循環 | 沒有退出條件 |
| 等待永不發生的事件 | 死鎖 |
| Context 未取消 | 忘記調用 cancel |

**預防措施**：

**1. 使用 Context 控制生命週期**：
```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

go func() {
    for {
        select {
        case <-ctx.Done():
            return  // 優雅退出
        case data := <-ch:
            process(data)
        }
    }
}()
```

**2. 確保 Channel 會被關閉**：
```go
go func() {
    defer close(ch)
    // 工作...
}()
```

**3. 使用 Buffered Channel 避免阻塞**

**4. 監控 Goroutine 數量**：
```go
runtime.NumGoroutine()
```

</details>

## 🌐 Echo、型別與記憶體

<a id="q15"></a>
### Q15: Echo 的 middleware、路由與短路應如何設計？
<!-- Concept ID: concept.go.echo.framework-architecture; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐ (6) | **重要性**: 🔴 必考

請說明 Echo 的全域、群組與單一路由 middleware 如何組成請求鏈，以及認證失敗時如何安全短路。

<details>
<summary>💡 答案提示</summary>

- 先區分全域、group、route middleware，再以實際註冊順序追蹤 request 前置、handler 和 response 後置。
- Recover／錯誤邊界要能覆蓋可能 panic 的 downstream；request ID、metrics 和 timing 要能記錄短路與錯誤結果。
- 認證、tenant 或 authorization 失敗後應回傳 401／403 並停止呼叫下一層，避免 response double write。
- 路由參數與原始 URL 不等同於資源授權；matched route、可信 claims 和 service／資料層 tenant 條件都要驗證。

</details>

### Q17: Go 泛型的 constraint 與 interface 應如何選擇？
<!-- Concept ID: concept.go.internals.generics-constraints; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐ (6) | **重要性**: 🔴 必考

請比較泛型型別參數、constraint、具體函數與 interface{}／reflection fallback 的使用邊界。

<details>
<summary>💡 答案提示</summary>

- any 是不限制型別的 constraint；comparable、~T 和 union constraint 應只表達真正需要的操作與底層型別集合。
- 泛型 constraint 是編譯期型別集合，不等同於 runtime interface value；不要為了抽象而把所有資料裝箱或反射。
- 泛型不保證零 allocation 或一定更快；用 benchmark、allocs/op、B/op、可讀性與 binary size 比較具體、泛型和 interface 實作。
- API 要保留清楚的 ownership，避免 generic wrapper 捕獲可變的 request、tenant 或 buffer state。

</details>

### Q18: 逃逸分析結果應如何解讀與驗證？

### Q19: sync.Pool 何時能降低 GC 壓力，何時會造成資料污染？
<!-- Concept ID: concept.go.standard-library.sync-pool; Learning Objective IDs: LO-1, LO-2, LO-3 -->

**難度**: ⭐⭐⭐⭐⭐⭐⭐ (7) | **重要性**: 🔴 必考

請說明 sync.Pool 的生命週期、reset 與 ownership 規則，以及它和可靠 cache、連線池的差異。

<details>
<summary>💡 答案提示</summary>

- Pool 是可丟棄的暫存物重用機制，物件可能在 GC 時被清空；Get 不能假設永遠命中，New 也可能不提供物件。
- 取出後要清除舊狀態，使用期間只能由目前 owner 存取；Put 後不能再讓其他 Goroutine 讀寫該物件或其 bytes。
- 若輸出要跨越 request 或交給 queue，應先複製資料或在明確同步完成後 Put；大 backing array 要有容量上限。
- 不要把 connection、transaction、tenant state、request context 或需要可靠保存的事件放入 Pool；用 benchmark、pool hit／miss、GC、RSS 和 P99 證明收益。

</details>
