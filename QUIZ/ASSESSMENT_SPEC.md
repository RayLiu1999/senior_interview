# 硬測驗規格 (Assessment Track)

這份規格定義如何把知識文章轉換成可驗證的硬測驗。現有 Quiz 保留作為快速複習與口頭自測；硬測驗則用來確認讀者能否在情境、故障與權衡取捨中實際運用概念。

## 核心模型

測驗的最小單位不是文章，而是**學習目標**。一篇文章可以拆成多個學習目標；每個重要學習目標至少應對應一個測驗，重要程度 4-5 的概念則應至少包含一題情境或診斷題。

```text
Concept
├── Article
├── Learning Objectives
├── Prerequisites
└── Assessment Items
    ├── Concept Check
    ├── Trace / Diagnosis
    ├── Scenario / Trade-off
    └── Implementation / System Design
```

## ID 規則

- **Concept ID**：`concept.<domain>.<topic>.<concept>`，代表可長期追蹤的知識概念。
- **Assessment ID**：`assessment.<domain>.<topic>.<assessment>.v<version>`，代表一個可獨立評分的測驗版本。
- ID 不使用中文標題、檔案名稱或難度，避免文章改名時破壞映射。
- 一題可以有一個主要 Concept ID 和零至多個次要概念，但評分時必須明確指出主要測試目標。

## 每個硬測驗必備欄位

- Assessment ID
- 主要 Concept ID
- 對應文章
- 題型、難度、重要程度與建議作答時間
- 測驗目標
- 題目情境與限制條件
- 作答要求
- 期待證據（回答中必須出現的推理、判斷或設計內容）
- 0-4 分評分規準
- 參考答案、常見失分點與延伸追問

## 題型與硬度

| 題型 | 驗證能力 | 適合內容 |
| :--- | :--- | :--- |
| 概念檢查 | 能否正確定義與區分概念 | 基礎名詞、核心原理 |
| 追蹤題 | 能否依序推導狀態、資料或訊息變化 | TCP、交易、併發、訊息佇列 |
| 診斷題 | 能否從症狀定位故障層級與原因 | 快取、可觀測性、Kubernetes、安全 |
| 情境／取捨題 | 能否在限制下選擇方案並說明代價 | API、資料庫、分散式系統 |
| 實作／設計題 | 能否產出可驗證的程式或架構 | 程式語言、系統設計、AI 後端 |

「硬」不等於單純增加名詞數量。硬測驗必須提供**限制條件、失敗情境或需要取捨的選項**，要求讀者說明推理過程，而不是只背出定義。

## 評分規準

| 分數 | 判定標準 |
| :---: | :--- |
| 0 | 無法建立正確模型，或核心判斷與題目情境矛盾 |
| 1 | 能背出部分定義，但無法套用到題目情境 |
| 2 | 主要結論大致正確，但缺少關鍵機制、限制或驗證方法 |
| 3 | 能正確分析情境，提出可行方案，並說明主要代價 |
| 4 | 能完整連結原理、故障模式、驗證數據與取捨，並指出方案的邊界條件 |

預設通過標準為 **3 分**；若題目標示為系統設計或生產事故診斷，可另外要求所有核心評分面向至少達到 2 分。

## 覆蓋率規則

1. 每篇納入硬測驗軌道的文章，先列出 3-6 個可觀察的學習目標。
2. 每個學習目標必須至少被一題 Assessment Item 覆蓋。
3. 重要程度 4-5 的文章至少要有一題情境／診斷／取捨題。
4. 文章與測驗必須雙向連結，且連結使用穩定 ID 對應的檔案。
5. 文章、測驗或 ID 改名時，必須重新執行連結與覆蓋率檢查。

## 與現有 Quiz 的關係

- **現有 Quiz**：適合快速複習、口頭回答與建立知識範圍，保留其「答案提示」形式。
- **硬測驗軌道**：適合正式自測，答案提示改為評分規準、期待證據與參考答案。
- 同一概念可以同時出現在兩條軌道，但兩者不應互相取代：快速 Quiz 驗證記憶，硬測驗驗證應用能力。

## 遷移順序

先以 TCP、資料庫交易、快取失效模式與 RAG 建立跨領域試點；確認 ID、題型、評分與導覽方式穩定後，再擴展到分散式系統、訊息佇列、Kubernetes、安全與系統設計。
